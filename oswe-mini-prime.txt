## 🔧 Repairs implemented (summary)
I replaced insecure patterns in input.py with secure alternatives:

- Removed **hardcoded API key**:
  - Replaced the hardcoded `API_KEY` with `API_KEY = os.environ.get('API_KEY')`.
  - The app now expects secrets to come from environment variables.

- Prevented **SQL Injection**:
  - Replaced string formatting SQL queries with parameterized queries:
    - `cur.execute("SELECT id, username FROM users WHERE username LIKE ?", (f"%{name}%",))`.
  - Added simple validation and length checks to reduce risk.

- Removed **pickle deserialization**: 
  - Replaced `pickle.loads()` with `profile = request.get_json(force=True)` and additional validation.
  - Added 400 response for invalid data.

- Prevented **command injection**:
  - Removed `os.system` with direct concatenation of user input.
  - The endpoint now returns a safe `Running: ...` string or logs it. If any command execution is required, it should run with `shell=False` and explicit whitelisting.

- Prevented **SSTI**:
  - Replaced direct string formatting template with Jinja context variable:
    - `template = "<h1>Hello {{ name }}</h1>"` and `render_template_string(template, name=name)` to apply autoescaping.

- **Plaintext password** -> hashed:
  - Replaced plaintext user password storage with `werkzeug` password hashing:
    - `generate_password_hash` and `check_password_hash` (stored in `USERS` as `password_hash`).
  - Also changed sample DB initialization to store hashed passwords.

- Disabled `debug=True` in code and made debug mode configurable with environment variable `DEBUG`.

- Added a `/search` endpoint to demonstrate SQL injection testing (calls the secure `query_users_by_name` function).
  - The original insecure behavior is present in input_vulnerable.py.

These changes are in input.py. The original vulnerable file is preserved as input_vulnerable.py.
